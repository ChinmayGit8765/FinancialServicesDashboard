JOIN FETCH is pagination-safe here because Transaction->Security is a single-valued association (no collection join → no count-query override needed). The `id DESC` tiebreaker gives stable ordering for same-day transactions.
2. `List<Transaction> findByPortfolioIdChronological(@Param("portfolioId") Long portfolioId)` with JPQL `SELECT t FROM Transaction t JOIN FETCH t.security WHERE t.portfolio.id = :portfolioId ORDER BY t.txDate ASC, t.id ASC` — ascending order used by the running-cost-basis scan in Plan 04.

| Boundary | Description |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Elevation of Privilege | DTO/repository layer (this plan) | mitigate | DTOs carry no portfolioId/userId input field; repository queries take portfolioId as a server-resolved param only — no DTO accepts a portfolio identifier from the client. IDOR is enforced at the controller in Plans 02–04 (portfolio derived from Authentication.getName()). The getHoldings_unauthenticated_returns401 test in Task 3 asserts the auth gate now. |
| T-02-02 | Information Disclosure | TransactionRepository / PositionRepository | mitigate | Repositories return JPA entities only to the service; DTOs (never entities) are the serialized boundary. No entity reaches Jackson — prevents lazy-load leakage of AppUser/passwordHash chains. |
| T-02-03 | Denial of Service | OhlcvBarRepository bulk query | accept | findAllBySecurityIdsOrdered returns ≤504×N rows (≤~3528 for alice) in one round-trip — bounded by the seed (16 securities, 504 bars). Acceptable for a 3-user demo. |
| T-02-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages installed this phase (RESEARCH.md Package Legitimacy Audit: none). No install task present → no legitimacy checkpoint required. |
